## 2. 三个硬核技术点

### 2.1 共享 WebGL 上下文的四个必要条件

```ts
// 1. 取 Cesium 的原生上下文
const gl = (viewer.scene as any).context._gl
// 2. 交给 Three（同一个 canvas）
new THREE.WebGLRenderer({ canvas: viewer.canvas, context: gl })
// 3. 绝不能擦掉地球
renderer.autoClear = renderer.autoClearColor = renderer.autoClearDepth = false
// 4. 每帧在 postRender 里同步相机并显式切回默认帧缓冲
renderer.setRenderTarget(null)
renderer.render(scene, camera)
```

少了第 4 步的 `setRenderTarget(null)`，Cesium 后处理期间绑定的离屏 FBO 会把 Three 的绘制吃掉——**drawCall 有、屏幕没东西**。

### 2.2 ECEF 局部化（float32 精度）

世界坐标量级 6.4e6，直接进 float32 会丢厘米级精度，表现为物体随相机移动抖动。
做法：`V' = V ∘ T(origin)`，在 JS 双精度里先乘好，再上传给 GPU。

> 注意方向：写成 `T(-origin)` 会让相机落到 2×origin 处（本次实测 `cameraLocal ≈ 1e7`），
> 画面全空但 `drawCalls > 0`，极难通过日志发现——必须把实例位置投影到 NDC 才能定位。

### 2.3 深度不通是这套方案的固有代价

Cesium 的投影矩阵 near/far 跨度极大（远平面 5e8），共享上下文里 Three 算出的 `z` 会塌到 `1.0`，
与 Cesium 写进深度缓冲的值相同，`depthTest` 一律失败——**262 个实例在视锥内却一个像素都不出**。

当前取舍：车辆与光柱关闭 `depthTest`（这类目标本就应始终可见）。
需要真实遮挡时的正确做法：开启 Cesium `logarithmicDepthBuffer` 并同步改造 Three 的着色器——
这是双引擎方案里必须提前预算的成本，不是能"顺手解决"的小问题。

## 3. 本次踩坑记录（按发现顺序）

| # | 现象 | 根因 | 修复 |
| --- | --- | --- | --- |
| 1 | `pnpm install` 报 corepack 404 | `packageManager` 锁定版本，corepack 拉不到 | 移除该字段，用本机 pnpm |
| 2 | `ERR_PNPM_IGNORED_BUILDS` 阻断安装 | pnpm 10+ 默认拦截依赖 postinstall 并升级为错误 | `pnpm-workspace.yaml` 里 `onlyBuiltDependencies` + `strictDepBuilds: false` |
| 3 | `server.adapter is not a function` | 在 Gateway `afterInit` 里挂 Redis Adapter，拿到的是 Namespace 且时机已晚 | 自定义 `RedisIoAdapter`，在 `createIOServer` 里挂 |
| 4 | 首屏场景全黑（相机高度 = 1m） | 俯角 offset 的 z 分量符号写反，相机被压到地面以下 | `-range * sin(pitch)` |
| 5 | 场景可见但 Three 物体全无（`drawCalls=1`） | 局部化矩阵用了 `T(-origin)`，相机跑到 2×origin 外 | 改 `T(+origin)` |
| 6 | 262 个实例在视锥内仍不可见 | 深度精度塌陷（见 2.3） | 关闭实例层的 `depthTest` |
| 7 | 车辆"看不见"其实是 3px | 5.2km 视距下 20m 车长只有 3~4 像素 | 视距压到 4km + 几何放大到约 60m（可视化夸张） |
| 8 | 车辆模拟启动时读不到路网 | `onModuleInit` 顺序不保证，PgService 连接池尚未建好 | 改用 `onApplicationBootstrap` |

## 5. 微服务拆分触发信号（与方案一致）

1. 轨迹消费 CPU 持续占满 NestJS 进程，加副本无法线性缓解（受分区数上限约束）；
2. GB28181 信令需要独立部署到靠近媒体服务器的网络位置；
3. 布控规则匹配复杂度显著上升（特征比对、多规则组合），需要独立资源与发布节奏。

拆分动作：把模块间的进程内调用换成 Kafka Topic。**今天的 Service 接口就是明天的服务契约**——
这也是模块化单体优先的根本理由。
